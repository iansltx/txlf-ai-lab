Part 1 · Lima

Lima — Linux Machines

  • CLI tool that launches Linux VMs…
  • …with automatic file sharing and automatic port forwarding
  • WSL2 energy — but for macOS and Linux
  • The whole machine is one YAML file you can put in git

⏱ 0:10. Definition first: Lima launches Linux virtual machines and handles the two things that are normally fiddly — sharing files in, forwarding ports out.

The last bullet is why we chose it: a README saying "install python, then ollama, then…" rots. A Lima template is the environment. Same file → same machine, on every laptop in this room.

Part 1 · Lima

A short history

  • 2021 — Akihiro Suda: run containerd/nerdctl on Macs
  • 2022 — joins CNCF (sandbox)
  • You may already run it: Colima · Rancher Desktop · Finch
  • Nov 2024 — v1.0
  • Oct/Nov 2025 — CNCF incubating; v2.0 targets AI workflows

Started May 2021 by Akihiro Suda, a containerd maintainer. Original itch: containers are a Linux kernel feature, Macs don't have one — give Mac users containerd + nerdctl. Turned out to be generally useful.

Lots of tools quietly build on it — if you've used Colima, Rancher Desktop, or AWS Finch, you've run Lima without knowing.

The punchline for us: Lima v2.0 (Nov 2025) made AI workflows a headline use case — running models and AI agents inside a VM so they can't touch your host. There's even a krunkit driver for GPU-accelerated local LLMs on Apple Silicon. We're not misusing a container tool today; we're using Lima exactly as its maintainers now intend.

Part 1 · Lima

Why a VM for AI work?

  • Isolation — the AI ecosystem loves curl | sh. Fine… in here.
  • Repeatability — fast-moving deps, pinned OS, zero "works on my machine"
  • Disposability — rebuild costs one command, so break things freely

Isolation: half the install instructions in this space pipe a shell script from the internet into root. Inside a VM that's a shrug, not a risk assessment.

Repeatability: model runtimes, Python packages, and system libs move fast and break each other. Pin the whole OS.

Disposability is the underrated one — when the environment is cheap to rebuild, you experiment more bravely. We will literally practice deleting a VM in about four minutes.

Part 1 · Lima

limactl in five commands


limactl start <template>    # create + boot (name, file, or URL)
limactl list                # what exists, what's running
limactl shell <name>        # a shell inside the VM
limactl stop  <name>        # shut down, state kept
limactl delete <name>       # gone. completely.

Bonus: shell drops you into your current host directory — if it's mounted.

That's genuinely the whole daily-driver surface. Templates can be built-in names (template://default), local YAML files (ours), or URLs.

The bonus behavior is why every lab starts with cd ~/ai-lab first — the host/guest boundary nearly disappears.

⏱ 0:18. DEMO first (2 min), then the room follows.

Beats to hit while they work:

1. uname -a: a real Linux kernel. whoami: your host username mirrored in.

2. ls ~: wait — those are your host files. Then touch fails: read-only file system. PAUSE HERE. This is Lima's most important default: your home is shared read-only. Writable access is opt-in, per-directory, in the template. Sandbox posture out of the box.

3. Delete without ceremony — this is the disposability muscle. Note the second VM boots fast: the Ubuntu image is cached.

If someone's start hangs: pair them, keep moving; troubleshooting section in the blog covers it.

Part 1 · Lima

Templates: the environment as a file


images:        # which OS, per CPU architecture
mounts:        # which host folders, read-only or writable
portForwards:  # which guest ports appear on the host
provision:     # scripts that run on first boot
probes:        # what "ready" actually means

A Dockerfile, but for a whole machine — and just as shareable.

Five verbs, that's the vocabulary. Everything else in a Lima template is refinement of these.

Analogy that lands: Dockerfile for a whole machine. Check it into git, send it to a colleague, "limactl start" is the new "works on my machine — here, have my machine."

Part 1 · Lima

Our lab, unabridged: ai-lab.yaml


images:                      # pinned Ubuntu 24.04 LTS (x86_64 + arm64)
cpus: 4
memory: "8GiB"               # 3B-model sized; 4GiB works too
mounts:
  - location: "~/ai-lab"     # ONLY this folder…
    writable: true           # …and writable, on purpose
portForwards:
  - guestPort: 11434         # Ollama API → host localhost:11434
    hostPort: 11434
provision:
  - mode: system             # first boot: python + ollama.com/install.sh
probes:
  - description: "ollama API to be ready"   # start ≠ done until it answers

⏱ ~0:31. DEMO: open the real file in your editor — this slide is the annotated skeleton.

What each block buys us: pinned image = repeatable in a year (the built-in default template tracks the newest Ubuntu — great daily, wrong for a lab). One writable mount = deliberate hole in the wall, not an open door. portForward = the model becomes a service your host can use. provision = the scary curl|sh lives in the sandbox. probe = "started" means "actually answering".

Land this line: this file is a deliverable of the workshop — everything we build travels with it.

Part 2 · Ollama

A short history

  • Early 2023 — Georgi Gerganov's llama.cpp: quantized LLMs on ordinary CPUs
  • Powerful, but a hacker's tool — compile flags, conversion scripts
  • Mid-2023 — Jeffrey Morgan & Michael Chiang launch Ollama
  • Their pedigree: built Kitematic → acquired by Docker
  • Result: "docker pull, for models" — library, Modelfile, standard API

Two projects made today possible. llama.cpp proved the industry assumption wrong: with 4-bit quantization, capable models run on laptops. Huge tinkerer ecosystem, GGUF file format.

But it was gloriously hostile to beginners. Ollama's founders had already built the friendly face of Docker once (Kitematic) — they did the same for local models: pull, run, a curated library, a Modelfile that works like a Dockerfile.

It became the default on-ramp, and its API — including an OpenAI-compatible endpoint — became the thing dozens of other tools integrate with. Started as a llama.cpp wrapper; has grown its own engine work since. Promise unchanged: one command between you and a running model.

Part 2 · Ollama

Quantization, one slide

llama3.2 — 3 billion parametersSize
Full precision (16-bit)≈ 6 GB
4-bit quantized (what you pulled)≈ 2 GB

Fewer bits per parameter · modest quality tax · this is why "LLM on a laptop" is a sentence.

"3B" = three billion learned numbers. Store each in 4 bits instead of 16 and the model fits in laptop RAM with room to spare. Quality cost is real but modest at this size.

Fun reveal: everyone in this room already pulled a 4-bit GGUF in Lab 0 without knowing — that's good defaults doing their job.

Part 3 · RAG

Three fixes, one winner

  • Retrain / fine-tune on your docs — slow, costly, redo on every edit
  • Paste everything into the prompt — context limits, diluted attention
  • Retrieve just the relevant passages, put them in the prompt ✓

Walk the two losers quickly. Fine-tuning: expensive and stale the moment a doc changes. Paste-everything: works until the corpus outgrows the context window — and you pay in speed and attention long before that.

The third one is Retrieval-Augmented Generation. Frame it now with the analogy on the next slide.

Part 3 · RAG

RAG = an open-book exam

At question time, find the right pages and hand them to the model inside the prompt.

  • Named by Lewis et al., 2020 (Facebook AI Research)
  • Roots: open-domain QA — DrQA, DPR, REALM
  • 2023: ChatGPT makes the limits everyone's problem → RAG everywhere
  • Refinements ever since — same core loop, and it's the one you'll build

The name comes from a specific 2020 paper out of FAIR. The idea is older — QA systems paired search with reading comprehension for years — but 2020's dense (neural) retrieval beat keyword search, and 2023's chatbot boom made grounding-in-your-own-data the industry's hello-world.

Everything since — hybrid search, rerankers, agentic retrieval — refines the loop we build in the next 40 minutes. Learn the loop, and the refinements are just knobs.

Part 3 · RAG

Embeddings: meaning as coordinates

  • A model that turns text into a vector (a long list of numbers)
  • Similar meaning → vectors point the same way (not similar spelling!)
  • Closeness = cosine similarity: 1.0 same direction, ~0 unrelated
  • Ours: nomic-embed-text — 274 MB, 768 dimensions

The load-bearing concept of the whole afternoon. "The candle smells like lavender and cedar" and "this wax melt has notes of lavender and wood" share almost no words — but their vectors sit close, and both sit far from "restart the server after updating the config."

That's the difference from grep: meaning, not spelling. Let's go see it as numbers.

Part 3 · RAG

Chunking

  • Whole files are bad retrieval units — one chunk ≈ one topic
  • Ours: split on blank lines, merge paragraphs up to 400 chars
  • Naive on purpose — readable beats clever, today
  • Chunk boundaries are where RAG bugs live (more later)

What do we embed? Not whole files — a file "about operations" matches everything vaguely operational. Few-hundred-character chunks make each vector about one thing, so retrieval can be precise.

Be honest: real systems fight hard here — structure-aware splitting, overlap, etc. Ours is 15 lines and works for tidy markdown. When their future RAG system misbehaves, chunking is suspect #2 (retrieval itself is #1 — coming up).

Part 3 · RAG

Vector databases

  • Persistence + fast nearest-neighbor search + metadata filters
  • Today: Chroma, embedded mode — a pip install, persists to a folder, SQLite inside
  • Outgrow it later → Qdrant, pgvector, … concepts transfer exactly

For 17 chunks you could brute-force compare in a loop. For a million you want a real index. Chroma (open source, early 2023) in embedded mode is perfect lab equipment: no server, no config, your knowledge base is a folder in the project.

Deliberate choice for a beginner workshop — and when they graduate to a served DB, every concept (collections, upsert, query by vector, metadata) maps one-to-one.

Part 4 · Assemble

The "framework" is an f-string


context = "\n\n---\n\n".join(chunks)          # the retrieved evidence

messages = [
  {"role": "system", "content":
      "Answer the question using ONLY the provided context. "
      "If the context does not contain the answer, say you don't know."},
  {"role": "user", "content": f"Context:\n{context}\n\nQuestion: {question}"},
]

Every RAG framework you'll ever meet is a fancier version of this string.

Read the system prompt out loud, slowly. Two instructions: use only this evidence; admit ignorance otherwise.

The "augmentation" in Retrieval-Augmented Generation is string formatting. Learning it this way first means LangChain and friends will never be magic — they'll be conveniences you can evaluate.

Part 4 · Assemble

Where it breaks (an honest list)

  • Retrieval misses — right chunk exists, doesn't come back → debug with search.py
  • Chunk boundaries split facts — neither half answers alone → smarter splitting
  • Small model fumbles — evidence is right there, synthesis wobbles → bigger model

Three failure sites, each testable in isolation — that's why we built it in layers. Search term for later: “RAG evaluation.”

⏱ ~1:42. Ending on honesty builds trust. The gift of the layered build: when their future system misbehaves, they know exactly which of three doors to check, and search.py checks door #1 with no LLM in the loop.

Evaluation of all this is a genuine engineering field now — plant the search term and move on.
